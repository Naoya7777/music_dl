# Music DL アーキテクチャ

## 1. 文書の目的

本書は、Music DL の現行実装について、構成、責務、処理の流れ、設計判断、運用上の注意を説明します。開発者、レビュー担当者、運用担当者を対象とします。

サービスの目的と要求は [プロジェクト概要](ProjectContext.md)、導入・操作・障害対応の手順は[使い方ガイド](Usage.md) を参照してください。
本書は将来像ではなく、現在の実装を基準にします。

## 2. 設計原則

Music DL は、画面、取得・変換、設定、入力検証を分けた小規模なレイヤード構成です。
「レイヤード構成」とは、役割ごとにプログラムを層へ分け、変更の影響を狭くする設計です。

設計では次を優先します。

1. 画面に `yt-dlp` や FFmpeg 固有の処理を持たせない。
2. URL、保存先、外部プログラムを信頼境界で検証する。
3. 取得・変換は別スレッドで動かし、画面部品の更新は画面側のスレッドだけで行う。
4. 実行状態の所有者を一つにし、二重実行を防ぐ。
5. 設定は検証済みの値として扱い、保存途中の破損を避ける。

サーバー、データベース、利用者認証は持ちません。外部接続先は YouTube、外部実行プログラムはFFmpeg、取得ライブラリは `yt-dlp` です。

## 3. システム境界と依存関係

```text
利用者
  │ URL、音質、保存先
  ▼
Music DL デスクトップアプリ
  ├── YouTube ─────── 音声と動画情報の取得
  ├── yt-dlp ──────── 取得処理と FFmpeg の呼び出し
  ├── FFmpeg ──────── MP3 への変換
  ├── 保存先フォルダ ─ 完成した MP3
  └── settings.json ─ 保存先と音質
```

| 依存先 | 境界で行うこと | 主な障害 |
| --- | --- | --- |
| 利用者入力 | URL の形式、単一動画、保存先を検証する | 空値、対象外 URL、存在しない保存先 |
| YouTube | `yt-dlp` を介して接続する | 非公開、地域制限、仕様変更、通信障害 |
| `yt-dlp` | オプションをサービス層で組み立てる | 互換性変更、取得失敗 |
| FFmpeg | 起動前と処理前に PATH 上の存在を確認する | 未導入、PATH 未設定、変換失敗 |
| ファイルシステム | 保存先を検証し、設定を原子的に置換する | 権限不足、容量不足、破損 |

PATH は、Windows が実行プログラムを探すフォルダの一覧です。「原子的な置換」は、設定ファイルを途中まで書き換えず、完成した一時ファイルと一度に入れ替える保存方法を指します。

## 4. 構成と責務

### 4.1. 起動境界

- `run.ps1` は Python Launcher と FFmpeg を確認し、必要な場合だけ `.venv` 仮想環境とPython パッケージを準備して、`.venv\Scripts\python.exe -m src.main` を実行します。
- `src/main.py` は `ModernUI` を生成し、画面のイベントループを開始します。
- デスクトップショートカットは利用者環境にだけ存在し、リポジトリでは管理しません。

仮想環境は、プロジェクト専用の Python とパッケージを分離する仕組みです。導入手順は[使い方ガイド](Usage.md#3-導入) に集約します。

### 4.2. プレゼンテーション層

`src/ui` は画面表示と利用者操作を担当します。

- `app_window.py` の `ModernUI` が、入力、設定変更、処理開始、進捗、結果、画面内ログを管理します。
- `theme.py` の `Theme` が、色、フォント、角丸などの表示値を一元管理します。
- ワーカースレッドからの通知を `queue.Queue` へ入れ、画面側が 50 ミリ秒ごとに処理します。
- 取得中は URL、貼り付け、保存先、音質、開始ボタンを無効にします。

### 4.3. コア層

`src/core` は画面から独立した処理を担当します。

- `download_service.py` の `DownloadService` は、FFmpeg の確認、`yt-dlp` の設定、ワーカースレッド、進捗と結果の通知、単一実行の制御を担当します。
- `config.py` の不変な `AppConfig` は、検証済みの保存先とビットレートを保持します。
- `config.py` の `ConfigManager` は、`settings.json` の読み込みと原子的な保存を担当します。
- `validation.py` は、YouTube の単一動画 URL と保存先フォルダを検証します。

## 5. 主要な処理の流れ

### 5.1. 起動と設定読み込み

1. `run.ps1` が実行環境を確認し、`src.main` をモジュールとして起動します。
2. `ModernUI` が `ConfigManager.load()` で `settings.json` を読み込みます。
3. 設定がない、または不正な場合は、保存先を利用者の `Downloads`、音質を 192 kbps にします。
4. `DownloadService.validate_environment()` が PATH 上の FFmpeg を確認します。
5. FFmpeg がない場合は理由を表示し、開始ボタンを無効にします。

### 5.2. 取得と変換

1. 画面が URL を検証し、サービス層が URL、保存先、FFmpeg を再検証します。
2. サービス層がロックを取得し、実行中でなければデーモンスレッドを開始します。
3. `yt-dlp` が最良の利用可能な音声を取得します。
4. 進捗率と推定残り時間を画面のイベントキューへ通知します。
5. `yt-dlp` の後処理として FFmpeg が選択されたビットレートの MP3 に変換します。
6. 成功時は完了、失敗時は URL を `[URL]` に置き換えたエラー概要を通知します。
7. 成否にかかわらず実行中状態を解除し、画面操作を戻します。

デーモンスレッドは、アプリケーション終了時に完了を待たずに終了するスレッドです。取得中の終了では確認画面を出しますが、終了を選ぶと処理完了は保証されません。

### 5.3. 設定更新

1. 利用者が保存先または音質を変更します。
2. 画面が新しい `AppConfig` を作ります。
3. `ConfigManager.save()` が UTF-8 の一時ファイルを書き、`settings.json` と置き換えます。
4. 失敗時は一時ファイルを削除し、画面へエラーを返します。

## 6. 状態、データ、インターフェース

### 6.1. 状態の所有者

| 状態 | 所有者 | 保護方法 |
| --- | --- | --- |
| URL、表示、現在設定 | `ModernUI` | 画面側のスレッドだけで更新 |
| 取得の実行中状態 | `DownloadService` | `threading.Lock` で読み書きを保護 |
| 画面への通知 | `ModernUI._ui_queue` | スレッド安全なキューを使用 |
| 永続設定 | `ConfigManager` | 検証後に一時ファイルから置換 |

### 6.2. 設定形式

設定は、通常プロジェクトルートに作られる `settings.json` へ保存します。

```json
{
  "save_dir": "C:\\Users\\user\\Downloads",
  "bitrate": "192"
}
```

`save_dir` は保存先、`bitrate` は 1 秒当たりの音声データ量を kbps 単位で表した文字列です。
許可値は `128`、`192`、`320` です。

### 6.3. コールバック

`DownloadService.run_download()` は、進捗、ログ、完了の三つのコールバックを受け取ります。
コールバックとは、処理中または処理後にサービス層から画面へ通知する関数です。この境界により、サービス層は画面部品を直接操作しません。

## 7. セキュリティ、信頼性、運用

- API キー、パスワード、Cookie を設定として保存しません。
- URL は YouTube の HTTP または HTTPS の単一動画に制限し、プレイリストを拒否します。
- 保存先は、存在する書き込み可能なフォルダであることを処理前に確認します。
- 通信タイムアウトは 30 秒、通常取得と分割データ取得の再試行は各 3 回です。
- エラー内の URL は画面表示前にマスクし、タイトルは表示可能な文字だけに制限して100 文字まで表示します。
- ログは画面のメモリ内だけに保持し、終了時に消えます。永続ログ、監視指標、警告通知はありません。
- 設定読み込みに失敗した場合は既定値へ戻し、警告を画面内ログへ出します。
- 設定保存に失敗した場合は、既存ファイルを途中まで上書きせず、画面に失敗を示します。

障害の具体的な切り分けは [使い方ガイド](Usage.md#8-トラブルシューティング) に集約します。

## 8. 検証方針

単体テストは、外部サービスや実際の FFmpeg を置き換え、次を確認します。

- 設定の既定値、読み込み、保存、破損時の復旧
- URL、プレイリスト、保存先の境界検証
- FFmpeg の存在確認
- `yt-dlp` のオプション、進捗計算、成功・失敗の通知
- URL のマスクとタイトルの安全な表示
- 実行中の重複開始防止

外部ネットワークと FFmpeg を使う自動結合テスト、画面操作テスト、実 MP3 の再生確認は未整備です。
リリース前は、自動テストに加えて、権利または許諾を確認済みの短い動画で手動の一連動作を確認します。
コマンドと合格項目は[使い方ガイド](Usage.md#9-動作確認とサポート) に示します。

## 9. 設計判断、リスク、改善候補

| 判断 | 採用理由 | 代替案とトレードオフ |
| --- | --- | --- |
| 小規模なレイヤード構成 | 画面と外部処理を分離し、単体テストしやすい | 単一ファイルは短いが変更の影響が広がる |
| `yt-dlp` をサービス層で包む | 画面を取得方法から分離できる | 画面から直接呼ぶとコードは減るが結合が強くなる |
| 標準 JSON とデータクラス | 現規模で依存を増やさず検証と保存ができる | Pydantic は検証を増やせるが依存も増える |
| スレッドと画面キュー | 同期式の取得処理と画面イベントを分離できる | `asyncio` は全面的な非同期設計と画面統合が必要になる |

主な改善候補は、設定を Windows の利用者別設定領域へ移すこと、キャンセルと部分ファイルの規則、構造化された永続ログ、依存先との契約テスト、画面操作テストです。
変更時は既存のインターフェースとデータ形式への影響を先に確認します。
